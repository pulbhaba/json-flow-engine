# 0001: Integrations (proposal)

Status: proposed. Task issues should treat the points below as the working
design and record any deviation here.

## Context

Workflows currently call external APIs by hard-coding `http.request` steps.
Users want ready-made integrations (HubSpot, OpenAI/ChatGPT, and similar, in the
spirit of Make.com modules) and an easy way for anyone, including an agentic AI,
to add new ones.

## Decision

- An integration is **declarative data**, not code: a JSON manifest describing
  a provider (base URL, auth scheme, allowed hosts) and its actions (name, input
  schema, request template, response mapping). Declarative manifests are easy for
  an AI to author and can be validated and sandboxed.
- Two sources, kept separate on disk:
  - `integrations/builtin/<provider>/integration.json`: shipped with the
    package, maintained in this repository.
  - `integrations/user/<provider>/integration.json`: user defined, never
    overwritten by upgrades. A user integration with the same provider id as a
    built-in one is a load error unless it opts in to override explicitly.
- Built-in integrations are **compiled in**: a build step generates a typed
  registry module from `integrations/builtin`. User integrations are
  discovered at startup from a configured directory (default `./integrations/user`).
- Workflows call an integration through an `integration.call` operation
  (`provider`, `action`, `input`, `credentials` reference). It expands to an
  HTTP request that still passes the URL policy, sandbox mocks, limits and
  redaction.
- Credentials are referenced by name and resolved from the environment or the
  run context; they never live in manifests or workflows.

## Consequences

- No manifest can execute code. New providers need no engine change.
- Authoring guidance for AI agents (template, schema, validation CLI) is part
  of the deliverable.

## Manifest format (refined in #2)

Implemented in `src/integrations/` and published as
`schemas/integration.schema.json` (generated by `scripts/write-schema.js`).

- Top level: `provider` (lowercase id), `baseUrl` (https only, no credentials,
  query or fragment), `allowedHosts` (exact lowercase hostnames, must include the
  `baseUrl` host), `auth`, `actions`; optional `schemaVersion` (`1`), `name`,
  `description`.
- `auth.type` is one of `none`, `bearer`, `basic`, `header` or `query`; `header`
  and `query` require a `name`. Manifests never hold secrets.
- Each action has an `inputSchema` (JSON Schema 2020-12, compiled by the
  validator), a `request` (`method`, `path` starting with `/`, optional `query`,
  `headers`, `body`) and an optional `response` (`output` mapping,
  `successStatus`, default any 2xx).
- Request and response values may hold `{{ }}` templates. The manifest
  validator checks only their structure; the expression scope is settled by
  `integration.call` (see below).
- Optional `overridesBuiltin` (boolean, user manifests): `true` is the explicit
  opt-in that lets a user manifest replace the built-in one with the same
  `provider` id (see Loader).
- Wildcard hosts are not supported in `allowedHosts`.

## Loader (refined in #3)

Implemented in `src/integrations/load.ts` (`loadIntegrations`). It only reads
and validates JSON; it never executes manifest content.

- Discovers `<dir>/<provider>/integration.json` one level deep under a builtin
  directory and a user directory (default `./integrations/user`, configurable).
  A missing user directory is not an error; a missing builtin directory is
  reported. Subdirectories without `integration.json` are ignored.
- The result keeps the sources separate and labelled: `builtin` and `user`
  lists plus a flat `errors` list. Each loaded entry records its `source`,
  `file` and whether it `overrides` a built-in one.
- The manifest `provider` must equal its directory name. Duplicate ids within a
  source are errors. A user manifest that reuses a built-in id is an error
  unless it sets `"overridesBuiltin": true`; then the user entry is active and
  the built-in one stays listed with `overriddenBy` set.
- Errors are reported per file (unreadable, invalid JSON, failed validation) and
  never stop other files from loading.
- The default user directory is resolved against the current working directory.

## `integration.call` (refined in #5)

Implemented in `src/operations/builtin/integration.ts`; registered by every engine.

- Config: `provider`, `action`, `input` (default `{}`) and `credentials`, the
  **name** of a credential (never the secret). `input` is validated against the
  action's `inputSchema` before anything runs (`INTEGRATION_INPUT_INVALID`).
- Template scope, settled here (resolving the question left open in #2):
  - Request template (`path`, `query`, `headers`, `body`): `input` is the
    validated action input. `steps` and `constants` are empty, so a manifest can
    never read workflow data it was not given. Values interpolated into `path`
    are percent-encoded; a resolved path may not contain `?`, `#` or dot segments
    and must stay on the `baseUrl` origin and in `allowedHosts`.
    `null` query and header values are omitted.
  - `response.output`: `input` is the HTTP response `{ status, headers, body }`
    (headers already redacted). Credentials are not in any scope.
- The request is expanded to an `http.request` config and executed by the same
  machinery, so the engine URL policy, response size limit, timeout, retry rules
  (method-aware), sandbox mocks (`mock("integration.call", ...)`, `allowLive`)
  and redirect refusal all apply. `allowedHosts` is checked in addition to the
  URL policy, never instead of it.
- Credentials are resolved at call time from the engine's
  `integrations.credentials` (an object or function: the run context), then from
  the environment variable `JSON_FLOW_CREDENTIAL_<NAME>` (name upper-cased,
  `-` to `_`). Arbitrary environment variables are not readable. `auth.type`
  decides placement; `basic` expects the secret as `user:password`. A manifest
  header with the same name as the auth header is replaced.
  A missing credential fails with `INTEGRATION_CREDENTIAL_MISSING`; mocks need none.
- The secret (and its base64 form for `basic`) is scrubbed from the output and
  from error messages and details; error causes are dropped.
- Sources: built-ins plus `integrations.user` passed to `createEngine`
  (typically from `loadUserIntegrations(dir?)`, default `./integrations/user`;
  the CLI `run` command loads the default). Collisions follow `combineIntegrations`
  and throw `INTEGRATION_INVALID` at engine construction.
- Not done: static (pre-run) checking that a provider/action exists; unknown ones
  fail at run time with `INTEGRATION_UNKNOWN`.
